# 報告書: GW（hgw）の GPU 高速化と、方法の自動選択

2026-09-27。計画書 [`gpu_fp32_plan.md`](gpu_fp32_plan.md) の段 0〜6 を実装・計測した結果。経過の記録は [`kBT_research.md`](kBT_research.md) の 03:50〜。
計測は kt1（RTX 5090 ×2、CPU 64 コア）、LiTi2O4 の `hgw` 1 回（6³ は `bench_hgw666`、9³ は `bench_hgw999`、`-np2 2`、`--use_fp32`）。

## 1. まとめ

*表 0* `hgw` 1 回の時間（kt1、RTX 5090 ×2、`-np2 2`、最終版 `2b2497c45`、四面体の重みの補助あり）

| | 旧コード（09-26） | fp32 | tf32 |
| --- | --- | --- | --- |
| LiTi2O4 6³ | 833 秒 | **424 秒（2.0 倍）** | **293 秒（2.8 倍）** |
| LiTi2O4 9³ | 5004〜5128 秒（83〜85 分） | **2990 秒（50 分、1.7 倍）** | **1975 秒（33 分、2.6 倍）** |

- **精度**: fp32 と倍精度の差は E_F から ±1 eV 以内の Re Σc で最大 0.02 meV、全体で 0.04 meV（以前の FP32 は 0.24 meV。誤差の主因を見つけて除いた、§5）。
  tf32（Σc の最後の積だけ TF32）は 0.8 meV。旧来の全部 TF32（`--mp` だけ）は 5 meV で、NiO のギャップが 0.1 eV ずれる
- **1 反復全体**: 6³ の `gwsc 1` は 12.5 分 → 9.3 分（fp32、最終版の一つ前で計測）。9³ は 88 分 → fp32 で約 55 分、tf32 で約 38 分の見込み。
  `--prec=tf32 --prec-final=fp32:N` で途中を tf32、最後の N 反復を fp32 にできる
- **倍精度（fp64）**: 1196 → 1110 秒（逆行列を FP32 の LU ＋ Newton 2 回、差は 9e-14 eV）
- **選ぶのは精度だけ**: `gwsc --prec=tf32|fp32|fp64`。どの積をどの方法で計算するかは、インストールの最後に計測ツール（`linalgtune_gpu`、約 30 秒）が
  その GPU で測って表にする。3 回とも同じ表になり、hgw で手で選んだ最速の組み合わせと一致した
- **同じ機械の別のジョブとぶつからない**: GPU ごとのロック。1 枚の GPU に小さな計算を 2 本同時に流すと、片方が待って両方とも正常に終わった
- **四面体の重み**を GPU の計算と並べて CPU で計算する（ファイルで受け渡し、ビット一致）
- **回帰テスト**: TestInstall の GW テストは GPU の fp64・tf32・fp32 と CPU で全部合格。`Samples/MLOQSGW`（NiO、GaAs）は fp32・tf32 とも合格
  （NiO のギャップは参照 2.066 eV に対し fp32 2.071、tf32 2.088 eV）
- **Ozaki（GEMMul8）**: 分解数で精度を 1 桁ずつ選べる。この GPU で速さに効くのは倍精度の積（7〜13 倍）。単精度では同じ精度の TF32 や実数 SGEMM に勝たない（§6）

## 2. 仕組み

```text
ユーザー:   gwsc ... --prec=fp32                    （tf32 / fp32 / fp64）
               │
呼び出し側: m_blas の gemm / 逆行列 zminv_eps_d      （呼び方は今まで通り。固定の行列には key= を付ける）

```

実数 SGEMM への組み替え: $C=\alpha\,\mathrm{op}(A)B$ の $B$（$k\times n$ 複素）と $C$（$m\times n$）をそのまま実数の $2k\times n$、$2m\times n$ とみなし、
$a=\alpha\,\mathrm{op}(A)_{jl}$ から実数行列を作る。

$$
A'_{2l-1,\,2j-1}=\mathrm{Re}\,a,\quad A'_{2l,\,2j-1}=-\mathrm{Im}\,a,\quad A'_{2l-1,\,2j}=\mathrm{Im}\,a,\quad A'_{2l,\,2j}=\mathrm{Re}\,a,
\qquad C = A'^{T}B \quad(\mathrm{op}=C,\,T)
\tag{1}
$$

$$
A''_{2j-1,\,2l-1}=\mathrm{Re}\,a,\quad A''_{2j,\,2l-1}=\mathrm{Im}\,a,\quad A''_{2j-1,\,2l}=-\mathrm{Im}\,a,\quad A''_{2j,\,2l}=\mathrm{Re}\,a,
\qquad C = A''B \quad(\mathrm{op}=N)
\tag{2}
$$

(2) の $A''$ は $A$ の列をそのまま実数として読んだ列と、その $i$ 倍の列を交互に並べたもので、写しは連続に読み書きできる。
積の演算数は複素 cgemm と同じ $8mnk$。RTX 5090 の cuBLAS の cgemm は FP32 で約 31 TFLOPS、この形は 50〜54 TFLOPS。

## 5. 分かったこと

1. **FP32 の誤差の主因は `build_zmel` の平面波の積（opA=N）だった**。この積を cuBLAS の cgemm から実数 SGEMM に替えると、倍精度との差が
   Re Σc で 1/5.7、SEx で 1/3.4 になった（S1c2）。長い和で桁落ちのある積で、cgemm と SGEMM の和の取り方の違いが出る。
   それまでの「FP32 の誤差は積の方法に依らない」（研究ログ 03:50）は、opA=C の積と大きい積だけを替えて比べた結論だった
2. **計測ツールは、測り方を誤ると誤った表を作る**。最初の表（S3）は hgw を 741 秒に遅くした。直した点は 4 つ:
   - 寸法を 64 の倍数（1024）で測ると GEMMul8 が有利に出る。実際の寸法（1053 など）に近い 1037 などで測る
   - 形ごとに hgw での時間の割合で重みを付ける（数秒しか使わない形が、何分も使う形と同じ重さで決めていた）
   - 単精度の積の誤差の上限を、同じ形での cuBLAS の誤差の 4 倍にする。GEMMul8 の 7 分解は行ごとに最大の要素に合わせて量子化するので、
     値の幅の広い長い和で cuBLAS の 4.8 倍の誤差になり、hgw では Im Σc を 1e-4 eV 動かした
   - **小さすぎる積には GEMMul8 を使わない**（64×64×64 未満か m·n·k < 1e8 なら cuBLAS）。これは表の閾値でなく GEMMul8 の性質なので backend に置いた。
     MP 版でも `readeigen` は固有ベクトルの MT 係数を (2l+1)×nband×(2l+1) の倍精度の積で回し（k 点ごとに数千回）、表が倍精度の積を GEMMul8 14 にすると
     これに 14 分解がかかって `build_zmel` が 110 秒遅くなった（S3 と S3b の遅れはこれ）
3. **この GPU の fp32 では GEMMul8 は選ばれない**。Ozaki が効くのは倍精度（大きな積でネイティブ FP64 の 7〜13 倍、誤差 1e-14 級）。
   逆行列の Newton の積もこれで速くなり、mixed1 は FP64 の LU の 7.5 倍速い（hgw の matinv は 83 → 11 秒）
4. 固定の行列をキーで保持する仕組みは、組み替えでは効く（Σc 実軸の小さな積が cuBLAS より速くなる）。GEMMul8 では大きな積で差が出ない
5. **tf32 の精度**: 昨夜（`fde20bd6c`）GPU に移した Hilbert 変換が、tf32 では TF32 の積になっていた。`Samples/MLOQSGW` の NiO（2 反復）で
   参照からのずれが 0.0135 → 0.04〜0.05 Ry に増えた（fp32 では 0.0005 Ry）。Hilbert 変換は 1 q あたり 0.7 秒なので、どの精度でも FP32 にした（`37e0a0f83`）
6. `findloc` は nvfortran では長さの違う文字列を空白で埋めずに比べる（表の行が読めなかった。ループで比べるように直した）
7. **nsys で見た残りの無駄**（6³、tf32、rank 0）: GPU がカーネルを実行していた時間は wall の約 7 割。`readeigen` が固有ベクトルの MT 係数を
   軌道ごとに (2l+1)×nband×(2l+1) の倍精度の積で回していて 115 万回・17 秒。全軌道を 1 つのカーネルにまとめて（`b8101dcb1`）6³ の hgw が
   tf32 で 314 → 293 秒、fp32 で 442 → 424 秒、9³ で 3180 → 2990 秒（fp32）。残りの待ちは OpenACC のカーネルごとの同期（560 万回）
8. 1 枚の GPU に 2 ランク（`-np2 4`）は、GPU の使用率が 75% から 95% に上がるが、時分割とメモリ上限で 38% 遅い。GPU 1 枚に 1 プロセスが正しい

## 6. 9³ をさらに速く: TF32 は Σc の積だけ、Ozaki の分解数

9³ の残りの 8 割は Σc の積なので、そこの精度を下げられるかを調べた。

*表 4* 6³ の `hgw`（重みはファイルから）。倍精度との差（meV）

| 構成 | 秒 | Re Σc（\|E−E_F\|<1 eV）最大 / rms | Re Σc（全体）最大 | SEx（\|E−E_F\|<1 eV）最大 |
| --- | --- | --- | --- | --- |
| fp32（自動の表） | 441.5 | 0.019 / 0.006 | 0.042 | 0.060 |
| **Σc の積だけ TF32（新しい `--prec=tf32`）** | **313.6** | **0.82 / 0.42** | 0.92 | 0.060 |
| 全部 TF32（旧来の `--mp`） | 284.0 | 5.1 / 2.2 | 24.2 | 3.2 |

NiO（`Samples/MLOQSGW`）のギャップ（2 反復後）: 参照 2.066 eV、fp32 2.069、Σc だけ TF32 2.088（+22 meV）、全部 TF32 2.035（1 反復後は −93 meV）。
新しい `--prec=tf32` で `Samples/MLOQSGW`（NiO、GaAs）と TestInstall の GW テスト（GPU）は全部合格（旧来の全部 TF32 では NiO が不合格だった）。

- 誤差を大きくするのは W を作る側（χ0 → 誘電行列の逆）。χ0 の足し合わせは正定値の和で誤差が乗りにくいが、W の小さな誤差が $(1-v\chi_0)^{-1}$ で拡大される。
  Σc の最後の積では誤差がそのまま入るだけなので、TF32 でも E_F まわりで 1 meV 未満に収まる
- → `--prec=tf32` を「Σc の最後の積だけ TF32、ほかは FP32」にした（`fc55b16da`）。旧来の `--mp` だけの指定（全部 TF32）は残してある
- `gwsc --prec-final=fp32:N`: 最後の N 反復だけ fp32 にできる（途中を tf32 で速く回し、最後を fp32 で締める）

*表 5* Ozaki（GEMMul8、fast）の分解数（1053 の寸法、行・列の値の幅 2 桁、誤差は倍精度との最大の相対差）

| 方法 | Σc 虚軸型 1053×8000×1053 | Σc 実軸型 1053×400×1053 | x0 型 1053×1053×4000 | 誤差 |
| --- | --- | --- | --- | --- |
| cuBLAS TF32 | 0.73 ms | 0.055 | 0.38 | 3e-4 |
| Ozaki 5 | 1.07 | 0.123 | 0.42 | 1e-4〜2e-4 |

- Ozaki は分解数 1 つで精度が約 1 桁変わる。精度の口としては使える（`--linalg=tf32.cgemm.large=gemmul8:6` で Σc の積を 1e-5 に）
- ただしこの GPU（RTX 5090）では、同じ精度なら TF32 か FP32 の実数 SGEMM が同等以上に速い。Ozaki がはっきり勝つのは倍精度だけ

1 反復全体は約 40 分の見込み（旧 88 分、fp32 約 58 分）。途中の反復を tf32 で、最後を `--prec-final=fp32:N` で fp32 にできる。

## 7. 使い方

```bash
python3 InstallAll.py --fc nvfortran --gpu --gemmul8 --bindir ~/bin   # 最後に linalgtune_gpu が表を書く（GPU が空いていれば）
gwsc 5 -np 32 -np2 2 --gpu --prec=fp32 <sname>                        # tf32 / fp32 / fp64
gwsc 10 -np 32 -np2 2 --gpu --prec=tf32 --prec-final=fp32:2 <sname>    # 途中は tf32、最後の 2 反復は fp32
```

- 表は `<bindir>/ecalj_linalg_policy.toml`。GPU を替えた・ドライバや CUDA を替えたら `linalgtune_gpu` を実行し直す。無ければ全部 cuBLAS（以前と同じ）
- 使われた表は `hgw` などの標準出力に 1 回出る（`linalg policy (fp32, from …)`）
- 手で上書き: `--linalg=fp32.cgemm.large=realsgemm,fp32.epsinv.large=mixed1`
- GPU ロック: `ECALJ_GPU_WAIT=<秒>` で待つのをやめる、`ECALJ_GPU_LOCK=0` で無効。`CUDA_VISIBLE_DEVICES` を設定すればその GPU からだけ取る
- 四面体の重みの補助: `--gpu` で自動。やめるときは `--no-tetwt-helper`

### 9.1 Σc のバッチを非同期に

### 9.2 tf32 の誤差の正体

tf32 と倍精度の Re Σc の差を Re Σc に当てはめると、差の 9 割近くは Σc の一様な縮みだった。

*表 10* 差 = a·Re Σc + b（6³、E_F ±1 eV の 192 状態 / 全 2544 状態）

| 構成 | 最大 | rms | a | 当てはめの残りの rms |
| --- | --- | --- | --- | --- |
| fp32 | 0.019 meV | 0.006 | ≈ 0 | 0.006 |
| tf32（Σc の積を TF32） | 0.82 | 0.42 | −4.8e-5（全体 −4.6e-5、相関 −0.90） | 0.13 |
| tf32（Σc の積を FP16） | 1.29 | 0.74 | −9.7e-5（全体 −6.7e-5） | 0.15 |

- cuBLAS の TF32 は入力を**最近接に丸めている**（先に最近接へ丸めた入力と結果がビット一致。切り捨てなら偏りは −7e-4）。
  それでも正の値の積で −4〜−7e-6 の偏りが残るので、原因はテンソルコアの**和の途中の切り捨て**。Σc では打ち消し合う和の途中の値が大きいので拡大される
- 入力を丸め直しても直らない。K を分けて FP32 で足し直しても、打ち消しの多い和では偏りは √(分割数) でしか減らず時間は 1〜3 割増える → やらない

### 9.3 FP16 の積（`realhgemm`）

*表 11* 実数の積 2106 × n × 2106（値は 3 桁の幅）、RTX 5090、FP64 に対する最大の相対誤差

| n | FP32 | TF32 | FP16 入力・FP32 の和 | BF16 入力・FP32 の和 | 誤差 TF32 / FP16 / BF16 |
| --- | --- | --- | --- | --- | --- |
| 16000 | 2.71 ms | 1.44 | **0.77** | 0.77 | 3.1e-4 / 3.1e-4 / 2.5e-3 |
| 8000 | 1.39 | 0.75 | **0.43** | 0.43 | 3.0e-4 / 3.0e-4 / 2.3e-3 |
| 1000 | 0.17 | 0.10 | **0.057** | 0.057 | 3.3e-4 / 3.3e-4 / 2.6e-3 |

- FP16 の仮数は TF32 と同じ 10 ビットなので入力の誤差は同じで、速さは 1.75〜1.9 倍。FP16 は 65504 で溢れるので、A'（W、キーで保持）と B を
  2 のべきで最大要素 2^14 未満にスケールする。B の最大は `cublasIsamax`、スケールと積の係数はデバイス上で決めて cuBLAS をデバイスポインタモードで呼ぶ
  （ホストは待たない）
- 計測ツールの候補に入れ、tf32 の行は Σc の形（虚軸・実軸・zsec）だけで重み付けした（tf32 の行を使うのは `--sigma_tf32` の Σc の積だけ）。
  RTX 5090 の表は tf32 = `realhgemm`（Σc 虚軸の形 0.71 → 0.51 ms）。fp32・fp64 の行は変わらない
- hgw では誤差が TF32 の積の 1.6 倍（E_F ±1 eV で最大 1.29 meV）。増えた分はほぼ一様な縮みで、組み替えで和の長さが 2k になった分、
  テンソルコアの和の切り捨てが多く効いているとみられる。tf32 の約束（10 ビットの入力、E_F まわり 1 meV 級）の範囲とみて採用した

### 9.4 q の割り振り

6³ の 2 ランクは、星の大きさの和は 110 対 110 で揃っていたが、W を作る回数が 9 対 8 で、片方が 14 秒遅れて終わっていた。LPT の重みに
「どの q も W を 1 回作る」分（平均の Σc の 1/3、コードの中の見積もりと同じ）を足した。q ごとの実測時間を使った見積もりでは、2 ランクの時間が
253.7 / 268.3 秒 → 259.2 / 262.8 秒になり、全体が約 5 秒（2%）縮む。
