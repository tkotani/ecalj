# GW（hgw）を FP32 オプションで速くする作戦（2026-09-27 案）

目的: `--mp --fp32` の GW を RTX 5090 ×2 ＋ CPU 64 コアで速く回す。精度は FP32 の積と同等以上。別の GPU や、
複数の計算が同時に走る状況でも、それぞれに合った方法が自動で選ばれるようにする。倍精度が要るときの道も残す。

## 0. いまの数字（LiTi2O4 6³ の `hgw` 1 回、kt1）

| 構成 | 秒 | 要点 |
|---|---|---|
| 基準（`c1b4b097a`）| 833 | |
| E1: Hilbert 変換を GPU へ | 722 | 1 q あたり 12 → 0.7 秒 |
| E2: E1 ＋ GEMMul8（単精度 7 分解）| 629 | Σc 虚軸 1.4 倍、誤差は FP32 の 1/3 |
| E4: E1 ＋ 実数 SGEMM への組み替え | **570** | 精度は FP32 のまま（Σc との照合は再実行中）|

- `gwsc 10` の 6³ 本番（E2 構成）は 1 反復 12.6 分（従来 16 分）
- 残る大物: Σc の行列積（まだ最大）、matinv（FP64 の LU、1 q 10 秒）、tetwt5（CPU 1 コア、9³ で 1 q 21 秒）

## 1. 行列積の選び方は、インストール時に計測して決める

GPU によって速い方法が違う（RTX 5090 は複素 cgemm が遅く FP64 が 1/64。H100 などは cgemm も FP64 も速い）ので、決め打ちにしない。

- `InstallAll.py`（GPU 版）の最後に計測ツールを回す。hgw の実際の形（$m=k\approx1000$、$n$ = 400〜5 万、正方 1000³、
  細長い 158×158×33 万）で、候補ごとに速さと誤差（FP64 の結果に対する）を測る
- 候補
  - 複素単精度: cuBLAS cgemm ／ 実数 SGEMM への組み替え ／ GEMMul8 単精度（6〜8 分解）／ TF32（`--fp32` なしのときだけ）
  - 複素倍精度: cuBLAS zgemm ／ cuBLAS のエミュレーション ／ GEMMul8 倍精度（12〜14 分解）
  - 逆行列（epstilde）: FP64 の LU ／ FP32 の LU ＋ Newton 1〜2 回
- 選ぶ基準: FP32 モードでは「誤差がネイティブ FP32 以下」の中で最速。倍精度モードでは誤差 1e-14 級の中で最速
- 結果は方針ファイル（`<bindir>/ecalj_gemm_policy.toml`）に、GPU 名と CUDA の版をキーにして書く。
  中身は演算の種類 × 大きさの区分ごとの方法と閾値
- 実行時は `m_blas` の初期化で読み、使った方針を stdout に出す。GPU 名が合わなければ内蔵の既定値にして警告する。
  オプション（例 `--gemm=cublas|real|ozaki`）で上書きできる

## 2. cgemm のラッパー（オプションの一つ）

`m_blas` の `cmm_d` の中だけで完結させ、呼び出し側は変えない。

- 実数 SGEMM への組み替え: $C$（複素、Re と Im が交互）を実数 $2m\times n$、opB=N の $B$ を実数 $2k\times n$ とみなし、
  $A$ だけを実数 $2m\times 2k$（各要素を 2×2 ブロック）に写すと、SGEMM 1 回で $C$ がそのまま出る。演算数は同じ $8mnk$
- 今は opA=C・opB=N・alpha=1・実数 beta のみ（`0e2ca543d`）。これを広げる
  - 任意の opA（写すときに転置・共役を済ませる）、複素 alpha（写すときに掛ける）、複素 beta（C に先に掛ける 1 パス）
  - バッチ版（`cmm_batch_d`、strided batched SGEMM）
  - opB=T/C は $B$ を写し直す（$B$ と同じ大きさの作業領域）
- どの方法を使うかは 1 の方針ファイルが決める。小さな積は cuBLAS のまま

## 3. Ozaki（GEMMul8）の位置づけ

- **FP32 モードの本命は実数 SGEMM への組み替え**: 同じ精度で Ozaki より速い（E4 570 秒 vs E2 629 秒。主要な積で 2.7 倍 vs 1.4 倍）
- **Ozaki の本命は精度を上げたいとき**
  - 単精度の模擬 8 分解は誤差 4e-8（FP32 の 1/30）で、cuBLAS の FP32 より速い
  - 倍精度の模擬 14 分解は 21 TFLOPS・誤差 4e-15（ネイティブ FP64 の 12 倍）。hgw 全体の倍精度の費用は E3 で測る
- 以上から、「FP32 と同じ精度なら組み替え、FP32 より上が要るなら Ozaki」とする。どちらを使うかは 1 の計測で機械ごとに決まる

## 4. CPU の使い方: 中心になるプロセスは GPU 1 枚に 1 つ、スレッドはブローカーに聞いて必要なときだけ

- MPI ランクは GPU 1 枚に 1 つのまま（ランクを増やすと GPU のクライアントが増え、GPU メモリも増える。`-np2 8` が止まった原因）
- CPU の重い部分（tetwt5、実軸の重み、CPU で解く逆行列など）は、そのプロセスからスレッドを出して回す
- スレッド数は、その都度ノード内の「ブローカー」に聞いて決める
  - ブローカー = ノードのファイル（flock。今の `/tmp/gpu.lock` と同じ仕組み）に、各 ecalj プロセスが使っているコア数・GPU を登録する
  - 空きコア = 全コア − 登録ずみ − ecalj 以外の負荷（`/proc/stat`）
  - 同時に走る複数の計算は、ブローカーを通して分け合う。GPU の割り当て（どの GPU か、共有するか）も同じ仕組みで扱う
- Fortran でスレッドを出す実際の手段は OpenMP の `num_threads(n)`（n はブローカーの答え）。
  ただし「OpenMP で全体を並列化する」のではなく、スレッドを出す道具としてだけ使う
  - 既定は 1 スレッドで、OMP_NUM_THREADS には従わない。MKL は 1 スレッドのまま
  - 対象の計算は、スレッド数が変わっても結果が変わらない形にする（tetwt5 は k を分担し、和の順序は直列と同じ）
  - 09-22 に外した OpenMP 版の問題（スレッドごとの whw のコピー、多ランクでのスレッド過多）は、この形なら起きない
