# 計画書: GW（hgw）の高速化を自動で選べる形にする

2026-09-27。対象は `hgw`（W の構築と Σc）と、それを回す `gwsc`。

## 1. 目的

- `--mp --fp32` の GW を、手元の RTX 5090 ×2 ＋ CPU 64 コアで速く回す。精度は FP32 の積と同等以上
- どの GPU でも、その機械で一番速い方法が自動で選ばれる。ユーザーが選ぶのは精度だけ
- 同じ機械で別の計算が同時に走っても、ぶつかって落ちない

## 2. 方針

| 方針 | 中身 |
| --- | --- |
| できるだけ単純に | 新しい仕組みは 4 つだけ: 振り分け表、方針ファイル、資源のロック、四面体の重みの受け渡し口 |
| 差し替え自由 | 計算の方法（backend）は 1 つずつ別のファイルにし、同じ呼び方にそろえる。足す・外すは表に 1 行 |
| 並列は MPI だけ | OpenMP は使わない。GPU 1 枚に中心のランク 1 つ |
| 速さの選択は自動 | インストール時に測って方針ファイルに書く。実行時は読むだけ（毎回同じ選択になり、結果も再現する） |
| ぶつからない | GPU は起動時にロックで確保し、実行中は共有ファイルに書かない |
| 将来の拡張の余地 | 資源のロックを 1 か所（ノードごとのディレクトリ）に集めておき、後でジョブ間の合図もそこでやり取りできるようにする |

やらないこと: OpenMP、実行中の自動計測、常駐のブローカー（デーモン）。

## 3. 全体の形

```text
ユーザー:  gwsc ... --prec=fp32          （tf32 / fp32 / fp64）
              │
呼び出し側:  m_blas の gemm / 逆行列     （今の呼び方のまま。固定の行列にはキーを付けられる）
              │
振り分け:    m_linalg_policy             （演算の種類 × 大きさの区分 × 精度 → backend）
              │   ← 方針ファイル（インストール時の計測）、既定の規則、手での上書き
              ▼
backend:    cublas │ realsgemm │ gemmul8 │ （将来の追加）      逆行列: lu64 │ mixed
```

### 3.1 振り分け表（`m_linalg_policy`、新規）

- 表の行は「演算の種類 × 大きさの区分 × 精度 → backend 名」。例:
  - fp32 の複素の積で、大きいもの（3 辺とも一定以上）→ `realsgemm`
  - 同じく小さいもの → `cublas`
  - fp64 の複素の積 → `gemmul8:14`
  - fp32 の逆行列 → `mixed1`
- 表の埋め方の優先順: 手での上書き（オプション）＞ 方針ファイル ＞ 既定の規則（すべて `cublas`、今と同じ動き）
- 起動時に、使う表を stdout に 1 回出す

### 3.2 backend（1 つずつ別ファイル、同じ呼び方）

| backend | 中身 | 状態 |
| --- | --- | --- |
| `cublas` | cuBLAS そのまま（FP32 / TF32 / FP64） | 今のコード |
| `realsgemm` | 複素の $A^\dagger B$ を実数 SGEMM 1 回に組み替え（$A$ だけ写す） | `ef0603458`（opA=C・opB=N のみ）→ 任意の opA、複素 alpha/beta に広げる |
| `gemmul8` | Ozaki（INT8）。分解数は精度ごとに固定。固定の行列は分解した形をキーで使い回す | 使い回しは未実装 |
| `lu64` / `mixed` | 逆行列: FP64 の LU ／ FP32 の LU ＋ Newton（1 回か 2 回） | `d992caefc`（既定は無効） |

新しい方法を試すときは、backend のファイルを 1 つ足して表に 1 行足すだけ。呼び出し側は触らない。

### 3.3 固定の行列の使い回し（Ozaki の効きどころ）

hgw には片方の行列を固定して何度も掛ける積がある。gemm に「この行列は前と同じ」を示すキー（周波数番号など）を
渡せるようにし、`gemmul8` はそのキーで分解した形を使い回す（GEMMul8 の `skip_scalA/B`）。他の backend はキーを無視する。

| 場所 | 固定される行列 | 使い回す範囲 |
| --- | --- | --- |
| Σc 実軸 | $W(\omega)$（周波数ごと） | 1 q の全 KXloop（約 840 回） |
| Σc 虚軸 | $W(i\omega)$（11 周波数） | 1 q の全 KXloop |
| Σc 虚軸（重みを積の後に掛ける形なら） | zmel | 11 周波数 |
| zmel の M2E 変換 | m2e の基底 | 1 q の全 KXloop |

使い回しの置き場（キャッシュ）は q ごとに捨てる。実軸の約 330 周波数ぶんは数 GB になるので、測ってから入れるか決める。

### 3.4 方針ファイルとインストール時の計測

- 計測ツール（`linalgtune`、新規）は、上の backend を実際に呼び、hgw の形（$m=k\approx1000$、$n$ = 400〜5 万、
  正方 1000³、細長い 158×158×33 万、使い回しあり・なし）で速さと誤差（FP64 の結果に対する）を測る
- 精度ごとに「誤差がその精度の約束以内で、最速」のものを選び、`<bindir>/ecalj_linalg_policy.toml` に書く
  （GPU 名、CUDA の版、ecalj の版、表の各行。数十行）。書き込みは一時ファイルから rename するので途中で壊れない
- `InstallAll.py`（GPU 版）の最後に回す。手でも回せる
- 実行時は読むだけ。GPU 名が違う・ファイルが無いときは既定の規則（`cublas`）にして警告を出す

### 3.5 精度のオプション

`gwsc --prec=tf32|fp32|fp64` を入り口にする（今の `--mp`、`--fp32` の組み合わせに対応させ、古い書き方も当面は通す）。
W や zmel を FP32 で持つか FP64 で持つか（実行ファイルの MP 版か倍精度版か）もこれで決まる。

### 3.6 同時に走る計算とぶつからないために

- **GPU**: 起動時に `flock` で GPU を 1 枚ずつ確保する（今の `/tmp/gpu.lock` を GPU ごとのロックに広げる）。
  確保できた GPU だけを `CUDA_VISIBLE_DEVICES` で渡す。空きが足りなければ待つか、はっきりしたメッセージで止まる。
  `flock` はプロセスが終われば外れるので、落ちたジョブのロックが残らない
- **GPU メモリ**: GPU 1 枚に 1 プロセスが原則。共有は既定で許さない（共有するときのメモリの見積もりは後で直す）
- **CPU**: ジョブごとに `-np` で割り当てる（今と同じ）
- **ファイル**: 作業ファイルはジョブのディレクトリの中だけ。方針ファイルは実行中は読むだけ
- **置き場所の一本化**: ロックは `/tmp/ecalj_res/`（ノードごと）に集める。将来、ジョブ間の合図（例:「GPU を空けてほしい」）を
  足すときも、ここに小さなファイルを置く形でできる。今は作らない

### 3.7 CPU の仕事（四面体の重み tetwt5）の受け渡し口

hgw の中では「重みをもらう」口を 1 つにし、中身を 3 通りから選ぶ。結果は同じ（ビット一致）で、選び方は自動
（補助ランクがいれば補助、ファイルがあればファイル、なければ自分で計算）。

| 中身 | 仕組み |
| --- | --- |
| 自分で計算 | 今のまま |
| ファイル | `gwsc` が hgw の直前に CPU の MPI の段（q で分担）を回して重みを書く。hgw は読む |
| 補助ランク | `mpirun -np N hgw : -np N htetwt`（MPMD）。`MPI__Initialize` で MPI_APPNUM ごとに分けるので hgw の中は変わらない。hgw の各ランクは担当する (q, spin) の並びを相方に 1 回送り、相方は順に計算して送る（自然に 1 個先読み） |

重みの配列を詰める・ほどく部品は、ファイルと MPI の両方で同じものを使う。

## 4. 進め方（段ごとに確かめてから次へ）

各段の確認:
(a) 6³ ベンチ（kt1 `bench_hgw666`）で SECU が基準と合う（ビット一致を狙う段はビット一致、FP32 の方法を変える段は 1e-5 eV 以内）。
(b) TestInstall の GPU テスト（`--gpu`、`--gpu --mp`）と [`Samples/MLOQSGW`](../../../Samples/MLOQSGW/README.md) に通る。
(c) `hgw` の時間を測る。
(d) 研究ログに書いてコミットする（push は指示があってから）。
開発は kt1 の `~/ecalj_dev`（`~/bin_dev`）で行い、本番の `~/ecalj` は走行中に触らない。

| 段 | 内容 | 完了の条件 |
| --- | --- | --- |
| 0 | 計測をそろえる: E3（倍精度 ＋ Ozaki の hgw）、空いた GPU でのマイクロベンチ、Ozaki の使い回しの効果 | 数字が研究ログにそろう |
| 1 | パッケージ化（動きは変えない）: `m_linalg_policy` を作り、既存の組み替え・GEMMul8・逆行列を backend として表の下に移す。gemm にキーの引数（まだ無視） | 既定の規則で今の結果とビット一致 |
| 2 | backend をそろえる: `realsgemm` を任意の opA・複素 alpha/beta へ、`gemmul8` にキーでの使い回し、逆行列の `mixed` を表に。表を手で指定して、それぞれ hgw で確かめる | 各 backend が精度の約束を満たす。速さの表ができる |
| 3 | 自動選択: `linalgtune` と方針ファイル、実行時の読み込み、`--prec` | kt1 で手で選んだ最速と同じ選択になる。再実行で同じ選択 |
| 4 | ぶつからない: GPU ごとのロックと `/tmp/ecalj_res/`。kt1 で小さな計算を 2 本同時に流す | 2 本とも正常に終わる。GPU が足りないときは待つか、分かるメッセージで止まる |
| 5 | tetwt5 の受け渡し口: まずファイル、次に補助ランク（MPMD） | 自分で計算した場合とビット一致。時間の比較で既定を決める |
| 6 | 倍精度モード（fp64）の確認 | 倍精度の結果（1e-14 級）と費用がそろう |
| 7 | 本番: 9³ の `gwsc 10`（必要なら 6³ も取り直し） | |

あとで必要になったら: GPU の共有（メモリの見積もりの修正）、ジョブ間の合図、LPT の重みを実測の時間に、GPU が q 点より多いときの分割。

## 5. いまの数字（LiTi2O4 6³ の `hgw` 1 回、kt1）

| 構成 | 秒 | Σc（Re）の差 |
| --- | --- | --- |
| 基準（`4fb6df3ba`） | 833 | — |
| Hilbert 変換を GPU へ（E1、`1fd5b4a70`） | 722 | 5e-6 eV |
| ＋ GEMMul8 単精度 7 分解（E2） | 629 | 6e-6 eV |
| ＋ 実数 SGEMM への組み替え（E4、GEMMul8 なし、`ef0603458`） | 571 | 2e-6 eV |

KXloop あたり（虚軸 / 実軸）: E1 0.169 / 0.085 s、E2 0.120 / 0.078 s、E4 0.103 / 0.064 s。
6³ の `gwsc 10`（E2 の構成）は 1 反復 12.6 分（従来 16 分）、9 反復後の MLO バンドは旧 v9 と rms 8 meV。
